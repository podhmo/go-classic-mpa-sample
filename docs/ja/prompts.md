# タスク：Go 標準ライブラリ中心の Issue Tracker を実装する

Go 1.27 以上を使用し、`net/http` と `html/template` を中心に、古典的な Multi-Page Application（MPA）として動作する Issue Tracker を実装してください。

これは設計案やコード断片を求めるタスクではありません。実際に動作するアプリケーションをリポジトリ内に完成させ、テスト・動作確認まで実施してください。

一度の作業で利用可能なプロトタイプを完成させることを目指します。

## 1. 目的

現代的な Web UI を、JavaScript に依存せず、Go の HTTP サーバーとサーバーサイド HTML レンダリングだけで構築する実例を作ります。

次の特徴を重視してください。

- 古典的な HTTP のリクエスト・レスポンスモデル
- ページ単位のナビゲーション
- HTML フォームによるデータ更新
- POST → Redirect → GET（PRG）パターン
- URL とクエリパラメータによる状態表現
- サーバーサイドテンプレート
- CSS による現代的で美しい UI
- シンプルで読みやすい Go コード

教材的な価値も重視しますが、説明のためだけに抽象化を増やさないでください。

## 2. 技術的制約

### 必須

- Go 1.27 以上
- `net/http`
- `html/template`
- `database/sql`
- SQLite による永続化
- 通常の HTML と CSS

SQLite のドライバには、CGO を必要としない `modernc.org/sqlite` を優先してください。

Go の標準ライブラリで実装できる機能には、基本的に外部フレームワークを使わないでください。

ルーティングには `http.ServeMux` を使い、`GET /issues/{id}` のようなメソッド・パスパターンを活用してください。

### 使用しないもの

- ~~JavaScript（インライン・外部ファイルともに禁止）~~ → 2026-11-15 に緩和: storybook で挙動を検証できる範囲なら使用可。宣言的な HTML/CSS を引き続き優先（`docs/ja/decisions.md`「JavaScript 方針」参照）
- TypeScript
- React、Vue、Svelte などの SPA フレームワーク
- HTMX、Turbo
- Tailwind のビルドツールや Node.js ベースのフロントエンド環境
- Gin、Echo、Fiber などの Go Web フレームワーク
- ORM
- Docker を起動の必須条件にすること

CSS は手書きでも、軽量な CSS ライブラリを参考にしたものでも構いません。ビルド工程なしで動作することを優先してください。

## 3. 実装する機能

### Issue 一覧

`GET /issues`

- Issue のタイトル、番号、ステータス、ラベル、作成日時を表示
- Open / Closed の表示切り替え
- キーワード検索（タイトル・本文）
- ラベルによる絞り込み
- 新しい順・古い順での並び替え
- ページネーション
- 絞り込み条件を URL のクエリパラメータに反映
- 空の検索結果に対する適切な表示

### Issue 詳細

`GET /issues/{id}`

- タイトル、本文、ステータス、ラベル、作成日時、更新日時
- コメント一覧
- コメント投稿フォーム
- Issue の編集
- Open / Closed の切り替え
- Issue の削除

Issue 番号は作成時に自動採番し、削除後も再利用しないでください。

### Issue 作成・編集

- タイトルは必須
- 本文は任意
- ラベルを選択できる
- 入力値を検証する
- 検証エラー時は入力内容を保持してフォームを再表示する
- 成功後は適切なページへ 303 See Other でリダイレクトする

フォームのバリデーションはサーバー側で実施してください。

### コメント

- Issue 詳細ページから投稿
- コメント本文は必須
- 投稿日時を表示
- 投稿日時順に表示
- 投稿後は Issue 詳細へリダイレクト

ユーザー管理は今回実装しません。コメントの投稿者は固定のローカルユーザーとして扱って構いません。

### ラベル

- 最初から Bug、Feature、Documentation、Enhancement などを用意
- Issue に複数のラベルを設定可能
- ラベルの色を CSS で区別
- 一覧でラベルをクリックすると絞り込み可能

ラベルの管理画面は必須ではありません。

## 4. UI / UX

GitHub Issues、Linear、現代的な管理画面などを参考にしつつ、独自のデザインにしてください。

目標は「JavaScript を使わなくても、ここまで見た目と使い勝手のよい Web アプリケーションを作れる」と感じられることです。

### デザイン方針

- ライトテーマを基本とする
- 落ち着いたニュートラルカラー
- 適度な余白
- 読みやすいタイポグラフィ
- 控えめな境界線と背景色
- ステータスやラベルを視覚的に識別できる
- デスクトップとスマートフォンの両方で使える
- 派手なアニメーションや装飾は不要
- 絵文字を UI アイコンの代用として多用しない

特に以下の画面を丁寧に作ってください。

1. Issue 一覧：検索、フィルター、状態表示が整理された画面
2. Issue 詳細：本文、メタデータ、コメントが読みやすい画面
3. Issue 作成・編集：入力しやすく、エラーを理解しやすいフォーム

フォーム、ボタン、リンク、テーブル、バッジのデザインに一貫性を持たせてください。

### アクセシビリティ

- セマンティック HTML を使用
- `label` と入力要素を関連付ける
- キーボードだけでも操作できる
- フォーカス状態を明確にする
- 色だけで状態を表現しない
- エラーメッセージを適切に関連付ける

JavaScript がないことを機能的な制約と捉えず、HTML の標準機能を積極的に使用してください。

## 5. HTTP の設計

HTTP のメソッドとリダイレクトを明確に扱ってください。

- GET は表示・検索などの読み取りに使用
- POST は作成・更新・削除などに使用
- 更新成功後は PRG を適用
- 削除のような破壊的操作は GET で実行しない
- 不正な入力は適切に処理
- 存在しない Issue は 404
- 不正なメソッドは 405
- HTML のエスケープを確実に行う
- POST フォームには CSRF 対策を実施する

HTML フォームで扱える HTTP メソッドを優先し、PUT/PATCH/DELETE を使うためだけに JavaScript や特殊な仕組みを導入しないでください。

## 6. 永続化

SQLite を利用します。

必要なテーブルやインデックスは実装時に設計してください。

- Issue
- Comment
- Label
- Issue と Label の関連

アプリケーション起動時に必要なスキーマを初期化してください。

DB ファイルのパスは設定可能にし、デフォルトではローカルのファイルを使ってください。

初回起動時にはデモ用の Issue を複数登録してください。

デモデータには以下のバリエーションを含めてください。

- Open / Closed
- 複数ラベル
- コメント付き Issue
- 比較的長い本文
- 作成日時の異なる Issue

ただし、すでにデータが存在する場合に起動のたびにデモデータを追加しないでください。

DB ファイルは Git の管理対象外にしてください。

## 7. Go のコード構成

過剰なレイヤー分割は避けてください。

以下の責務を読み分けられる構成にします。

- HTTP ハンドラー
- データアクセス
- HTML テンプレート
- CSS・静的ファイル
- アプリケーションの起動処理

必要ならパッケージを分割して構いませんが、小規模なプロトタイプに見合った構成を選択してください。

Go の慣用的なエラーハンドリング、`context.Context`、`database/sql` のクエリ引数などを適切に利用してください。

テンプレートの共通レイアウト、ページ固有部分、共通部品の扱いにも注意してください。

CSS とテンプレートは `embed.FS` を使ってバイナリに埋め込んでも構いません。

シングルバイナリで動作可能な構成が望ましいです。

## 8. セキュリティと堅牢性

ローカル利用を想定したデモですが、基本的な Web アプリケーションとして不適切な実装は避けてください。

- SQL インジェクション対策
- XSS 対策
- CSRF 対策
- フォーム入力サイズの制限
- 適切なエラーレスポンス
- サーバー内部のエラー情報を画面へ漏らさない
- 削除操作の確認画面
- 更新操作の適切なトランザクション処理
- HTTP サーバーの適切なタイムアウト設定

認証・認可は今回のスコープ外です。ローカル専用の単一ユーザーアプリケーションとして設計し、デフォルトでは localhost にバインドしてください。認証なしで公開ネットワークへ配置できるアプリケーションであるかのようには説明しないでください。

Issue 本文とコメントはプレーンテキストとして保持・表示してください。Markdown やユーザー入力 HTML のレンダリングは今回不要です。改行は CSS などで保持してください。

## 9. テスト

`go test ./...` でテストが実行できるようにしてください。

最低限、以下を確認してください。

- Issue の作成・取得・更新・削除
- Open / Closed の切り替え
- コメント投稿
- 検索と絞り込み
- 入力バリデーション
- 存在しない Issue の 404
- POST 成功後のリダイレクト
- HTML エスケープ
- データの永続化

HTTP のテストには `httptest` を活用してください。

テスト用データベースは一時的な SQLite DB を使い、テスト間で状態が混ざらないようにしてください。

## 12. 作業の進め方

まずリポジトリの既存構成を確認してください。既存コードがある場合は、その目的を尊重し、無関係な変更を避けてください。

その後、以下の流れで進めてください。

1. 必要最小限の設計を決定する
2. SQLite のスキーマとデータアクセスを実装する
3. HTTP ハンドラーとテンプレートを実装する
4. CSS を整え、画面を仕上げる
5. テストを追加する
6. ビルド・テスト・動作確認を行う
7. 問題があれば修正する
8. README を整備する

作業途中で設計案だけを返して終了しないでください。

細かな設計判断については確認を求めず、今回の目的と制約に沿って自律的に決定してください。

実行環境にブラウザが利用可能なら、実際にページを表示して視覚的にも確認してください。利用できない場合は、HTTP レスポンスと生成 HTML、CSS の整合性を検証してください。

時間や実行環境の制約で完了できない項目がある場合は、実装済みの範囲と未検証・未完了の範囲を明確に区別してください。
