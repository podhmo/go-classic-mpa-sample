# i18n（日本語/英語）適用の調査・設計メモ

調査・設計メモ（実装前の検討段階 + 1 画面プロトタイプの評価記録）。
`pull-requests.md` / `live-updates.md` 等と同じ形式。

問い:

> この MPA に i18n を適用したい。言語は**英語（デフォルト）と日本語**の 2
> つで十分。実施方法の選択肢を全部洗い出し、1 画面だけプロトタイプして
> 評価したい。

結論を先に書くと:

- **おすすめは案C（薄い自作カタログ）+ 方式②（cookie + `?lang=` スイッチャ）**。
  stdlib のみで済み、このコードベースの「依存を増やさない」「embed で単一
  バイナリ」の方針と一致する。将来フォーマットを育てたくなったら案A
  （`golang.org/x/text/message`）への載せ替え面は小さい。
- プロトタイプは `/w/{ws}/issues`（一覧画面）に案Cを適用した。評価は
  末尾の「プロトタイプ評価」節。

## modern web guidance で気にするべき事柄

`npx modern-web-guidance` で関連ガイドを検索・取得した結果、このアプリで
実際に効いてくるルールは以下（ガイド id 付き）。

- **`html` / `accessibility`**: `<html lang>` は**ページの主言語に合わせて
  変える**（WCAG 3.1.1 Language of Page, Level A）。本文中で言語が変わる
  部分にはその要素に `lang` を付ける（3.1.2 Language of Parts, Level AA）。
  中身と違う言語コードを付けてはいけない — スクリーンリーダーが読み上げ
  言語を誤る。現状 `layout.html` は `<html lang="en">` 固定。
  `hyphens` など locale 依存 CSS の挙動も `lang` に連動する。
- **`ime-safe-enter-submit`**: 日本語入力では変換確定の Enter が keydown
  に来る。Enter-to-submit を自前で実装する場合は `event.isComposing` または
  `keyCode === 229` のガードが必須。本アプリは `enter-submit.js` が
  **Ctrl/Cmd+Enter 送信**なので素の Enter を拾わず現状は非該当 — ただし
  「Enter で送信」系を将来足すときの注意事項として残す。
- **`translator` / `language-detection`**: ブラウザ内蔵の機械翻訳・言語検出
  API は **volatile（単一エンジン実装、仕様変化あり）** で、ガイド自体が
  プロジェクト明示 opt-in 制。zero-JavaScript 方針とも衝突するため
  **採用しない**（案Eとして記録だけ残す）。
- **日時・数の書式**: `fmtTime` が `"Jan 2, 2006 15:04"` で固定。ロケールごと
  の書式化が要る（Intl 相当のサーバ側フォーマット。ガイド
  `calculate-event-differentials` はブラウザ側 `Intl.DurationFormat` の話だが
  「絶対時刻のみ表示」の本アプリではサーバ側で同じ問題を解く）。
- **キャッシュ**: `Accept-Language` でコンテンツを変えるなら
  **`Vary: Accept-Language`** を必ず出す。現行 `securityHeaders` の Vary は
  `Sec-Fetch-Site` / `Origin` のみ。

## 文字列の所在（現状調査）

「英語」が埋まっている場所はテンプレートだけではない。洗い出したもの:

| 層 | 場所 | 例 |
|---|---|---|
| テンプレート | `internal/web/templates/*.html` 全般 | "Issues" "New issue" "Open"/"Closed" "Previous"/"Next"、`aria-label`、`placeholder` |
| ビューモデル | 各ハンドラが組み立てる `Title` / `Heading` / `SubmitLabel` | `"New issue"`, `fmt.Sprintf("Edit issue #%d", id)` |
| バリデーション | `internal/store/validate.go` の `FieldErrors` | `"Title is required."`, `"Slug must match ..."` |
| エラーページ | `renderError*` の呼び出し箇所 | `"Form too large"` 等の heading/message |
| 日時 | `fmtTime`（web.go） | `"Jan 2, 2006 15:04"` |
| 静的 JS | `static/toast.js` / `partial-submit.js` 等 | `"Comment posted."`, `"Posting…"`, `"Comments (N)"` |
| フォールバック語 | `authorName` | `"anonymous"` |
| 列挙値の表示 | `store.HideReasons`、status バッジ | `"spam"` `"Open"` 等 |

一方**翻訳しないもの**: issue のタイトル・本文・コメントなどユーザー生成
コンテンツ（UGC）、workspace 名、ラベル名。これらは投稿者の言語のまま出す
（理想はコンテンツ言語を検出して `lang`/`dir` を付けることだが、今回の
2 言語 UI ではスコープ外）。

## 決めるべきことの分解

2 つの直交する軸がある。

1. **言語をどう決めるか**（リクエスト → ロケール解決）
2. **メッセージをどこに置いてどう引くか**（カタログ + テンプレート結合）

### 軸1: ロケール解決方式

| 方式 | 仕組み | 長所 | 短所 |
|---|---|---|---|
| ① `Accept-Language` のみ | ヘッダを言語タグにマッチング | 実装最小 | ユーザーが上書きできない。「ブラウザ設定が ja だが英語で見たい」を解決できない（アクセシビリティ上も非推奨） |
| ② cookie + `?lang=` スイッチャ | `?lang=ja` で cookie を Set してリダイレクト、以降は cookie。未設定なら `Accept-Language` → `en` | 切替 UI が zero-JS で作れる（ただのリンク）。URL 構造を変えない | cookie 変更が GET に乗る（言語切替では一般的に許容）。`Vary: Accept-Language` は初回訪問のため要る |
| ③ URL パス prefix `/ja/...` | `/ja/w/x/issues` | 言語つき URL が共有できる。SEO に強い | mux の全ルートを prefix 配下に複製 or パターン書き換え。`issuesURL` 等の全 URL ビルダにロケールを通す。手数最大 |
| ④ アカウント設定 | `users.lang` カラム + 設定画面 | ログインすればどの端末でも同じ | 未ログイン（匿名可の本アプリでは大多数）に効かない。設定画面を作るコスト |

本アプリは localhost 用途・匿名可・SEO 不要。**② が現実解**。③ は「URL を
共有した相手と同じ言語で見たい」が要件に入ったときの再評価先。④ は
accounts Phase 2 以降の任意拡張。

### 軸2: カタログ/実装案

| 案 | 内容 | 依存 | 複数形 |
|---|---|---|---|
| **A** `golang.org/x/text/message` | `message.NewPrinter(lang).Printf`、カタログは `message.SetString` でコード登録（または `gotext` で po 抽出）。CLDR 複数形あり | x/text（準標準） | あり |
| **B** `github.com/nicksnyder/go-i18n/v2` | TOML/JSON メッセージファイル + `Localizer`。go-i18n CLI でテンプレートから抽出 | 外部ライブラリ + ファイルフォーマット | あり（CLDR） |
| **C** 自作の薄いカタログ | `map[lang]map[key]string` を embed した JSON/Go ソースで持ち、`T(key, args...)` = `fmt.Sprintf`。テンプレートにはロケール束縛の `{{t "key"}}` | なし | なし（ja/en では手書きで十分） |
| **D** 言語別テンプレート複製 | `issues.en.html` / `issues.ja.html` を別ファイルでパース | なし | n/a |
| **E** クライアント側翻訳 | サーバは英語のまま、ブラウザの Translator API で表示時に翻訳 | なし（JS） | n/a |

各案の評価:

- **A（x/text/message）**: Go の「公式寄り」な答え。`language.Tag` の
  マッチング（`Accept-Language` パース）も x/text にある。ただしカタログ
  登録はコード生成/手書き Go が前提で、テンプレート文字列の抽出ツールは
  事実上 `gotext`（別ツール、go 1.x 未対応期が長い）。プリンターはロケール
  ごとに要るのでテンプレート側は「ロケール別パース」か「`.T` をビュー
  モデルに載せる」かの設計が必要。
- **B（go-i18n）**: 機能は最も揃う（複数形・複合・ファイル監視）が、
  ja/en のみ・複数形ほぼ不要の本アプリには過剰。依存追加のコストに見合わ
  ない。
- **C（自作）**: カタログを `internal/web/i18n/{en,ja}.json`（embed）に置き、
  `parsePages` をロケール別に回して `{{t}}`/`{{lang}}` を束縛するだけ。
  `{{t}}` が未登録キーなら en → キー名の順にフォールバックで段階導入し
  やすい（一部画面だけ訳せる）。複数形は英語なら `one/other` の分岐程度で
  手書き可能（今回の画面に真の複数形はない）。
- **D（テンプレート複製）**: 機構が一番単純だが、**構造の複製**が 2 倍に
  なる。片方だけ修正し忘れる事故が確実に起きる。翻訳抜けの検出手段もない。
  除外。
- **E（クライアント翻訳）**: サーバ側コストゼロだが、modern-web-guidance で
  volatile opt-in 対象、単一エンジン、zero-JS 方針違反、非対応ブラウザは
  英語のまま。除外。

### テンプレートへの束ね方（案C/A 共通の設計点）

`funcMap` はパース時固定なので、リクエストごとのロケールを「見せる」方法
が設計の肝:

1. **ロケール別テンプレートセット** — `parsePages(locale)` で `t` と
   `lang` をロケールに束縛して `pages[locale][page]`。テンプレートは
   `{{t "issues.title"}}` `<html lang="{{lang}}">` と書ける。**ビュー
   モデルを一切変えずに `<html lang>` まで届く**のが利点。パースコストは
   ロケール数倍（2 言語なら実害なし）。
2. **ビューモデルに `T` メソッド** — `{{.T "key"}}`。データ側でロケールを
   運ぶので `layout.html` からも使えるが、全ページ構造体（15+）と
   `dict()` 経由のフラグメントに `T` を配線する必要がある。
3. **`{{t . "key"}}` で第 1 引数にデータを渡す** — パースは 1 組で済むが
   呼び出しが冗長になり、`dict()` で組み立てるフラグメントにも手動で
   `"T"` を詰める必要がある。

プロトタイプは **1（ロケール別セット）** を採る。ビューモデル無変更で
layout まで訳せるため。

## 推奨案

- **言語解決**: ミドルウェア `withLocale`。優先順位
  `?lang={en,ja}`（cookie セット + `lang=` を除いた URL へ 303）→
  `lang` cookie → `Accept-Language`（`ja*` なら ja）→ `en`。
  ロケールは request context に入れる。`Vary: Accept-Language` を追加。
- **カタログ**: 案C。`internal/web/i18n/` に `en.json` / `ja.json` を
  embed。`T(lang)` が `func(key string, args ...any) string` を返す。
- **テンプレート**: `parsePages(locale)` で `t`/`lang` を束縛した
  ロケール別セット。`layout.html` の `<html lang>`、nav、footer と
  `issues.html` を訳す。言語スイッチャはヘッダ nav に
  `?lang=ja`/`?lang=en` へのリンク（クエリ保持は後述の残課題）。
- **ハンドラ側の文字列**: `Title`/`SubmitLabel` 等は `T(ctx, key)` で
  ロケールから引く（context に入れたロケールを使う）。
- **scope 外（今回やらない）**: store 層のバリデーションメッセージ、
  エラーページ文言、静的 JS の文字列（toast 等）、UGC の `lang` 付け。
  これらは全面適用時の課題として列挙する。

## 全面適用時の残課題（プロトタイプの外）

- store 層 `validate.go` の `FieldErrors` をロケール非依存にするには、
  「エラーをコードで返して web 層でメッセージ化」か「ctx のロケールで
  store が訳す」かの分岐が要る。前者がレイヤリングとして正しい。
- 静的 JS の文字列は `<html lang>` に連動した data 属性 or ロケール別
  配信で対応する必要がある（CSP `script-src 'self'` なので inline 埋め込み
  は不可 — `<html lang>` 読みか `data-*` 経由が妥当）。
- UGC の `lang`/`dir`: 理想は本文の言語を保存時に判定して `<article lang>`
  に出すこと。検出は golang.org/x/text にはない（whatlang 系か手掛かり実装
  が必要）。
- `Vary: Accept-Language` を付けると、Speculation-Rules の prefetch と
  キャッシュまわりの整合を再確認する。
- スイッチャリンク `?lang=ja` は現 URL の他クエリ（`?q=` 等のフィルタ）を
  落とす。フィルタ保持が要件なら `Referer`/r.URL を使って組み立てる。

## プロトタイプ評価（案C、`/w/{ws}/issues`）

ブランチ `devin/*-i18n-prototype` に実装した。構成は上記「推奨案」どおり:

- `internal/web/i18n.go` — カタログ embed 読み込み、`T(lang)`、
  `withLocale` ミドルウェア、context からの `tr(r, key)`。
- `internal/web/i18n/{en,ja}.json` — それぞれ ~35 キー。
- `render.go` — `pagesByLang[locale][page]`（`parsePages(locale)` で
  `{{t}}`/`{{lang}}` を束縛）、`executeLang` でフォールバック。
- `layout.html` / `issues.html` — `{{t}}`/`{{lang}}` に置換。ヘッダに
  言語スイッチャ（`?lang=` リンク）。
- `issues.go` — `Title: tr(r, "issues.title")`、`renderIssueList` に
  ロケールを渡す（他ページは既定 en）。
- `securityHeaders` — `Vary: Accept-Language` 追加。

### 動作確認（実サーバ + curl + ブラウザ）

- `GET /w/default/issues?lang=ja` → 303 + `Set-Cookie: lang=ja`、別の
  クエリはリダイレクト先に保持される。
- `Cookie: lang=ja` → `<html lang="ja">`、見出し「イシュー」、タブ
  「オープン/クローズ/すべて」、件数「1 件中 5–5 件を表示」、フッタ
  訳文まで出る。
- `Accept-Language: ja`（cookie なし）→ ja 描画。`Vary` に
  `Accept-Language` が載る。
- cookie `lang=fr`（未知）→ en にフォールバック。`go test ./internal/web`
  で i18n_test.go 6 件 + 既存テスト全パス。

### 良かった点

- **ビューモデル無変更**: `{{t}}`/`{{lang}}` をパース時に束縛する形にした
  ので、15+ ある page 構造体にフィールドを足さず `layout.html` の
  `<html lang>` まで届いた。全面適用時もこの形で横展開できる。
- **段階導入が自然**: 未翻訳キーは en→キー名の順でフォールバックするので、
  訳した画面だけ ja になる「部分適用」が壊れない。
- **typed renderXxx が安全網になった**: シグネチャ変更に伴う修正漏れ
  （storybook）はコンパイルエラーで即検出できた。
- 2 言語のテンプレートパース増は起動時の一回コストのみで体感なし。

### 痛かった点・見つかった制約

- **`{{if eq lang "en"}}` は関数値同士の比較になり常に不等** — `lang` は
  関数なので `{{if eq (lang) "en"}}` と括弧で呼び出す必要がある。一度はまり
  かけた（テンプレートの関数名は引数位置では自動呼び出しされない）。
- **context キーの iota 衝突**: `contextKey` 型の `const x = iota` を別
  ファイルに置くと auth.go の `userContextKey` と同値 0 になりサイレントに
  キーが衝突する。`iota + 100` で回避（pitfalls.md にも記録）。
- **文中リンクはキー分割で妥協**: "Try a different keyword or <a>clear the
  filters</a>." は 3 分割にしたが、文末の "." が en 語順を仮定していて ja
  では "…フィルタをクリア." と半角ピリオドが残る。本格運用ではメッセージ
  内にリンクのプレースホルダを許す仕組みか、文全体をパーシャル化する
  設計が要る。
- **スイッチャは他クエリを落とす**: `/issues?q=x` 上で `?lang=ja` を踏むと
  `q` が消える（`lang` 以外を href に含めるにはリクエスト依存の URL 生成が
  要り、パース時束縛では渡せない。ビューモデル or ヘッダで URL を組み立てる
  改修が必要）。
- **`fmtTime` は英語フォーマットのまま**: "Nov 13, 2026 17:20 にオープン"
  と混在する。ロケール別書式はカタログではなく Go 側の書式切替で対応要。
- **validation/エラーページ/JS 文字列は未対応**: 422 時のフォーム再描画で
  store 由来の英語メッセージが ja 画面に混ざる。次にやるならここ。

### 評価まとめ

案C（薄い自作カタログ + ロケール別テンプレートセット + cookie/?lang=
スイッチャ）は **実装 ~150 行 + 2 JSON で成立し、このリポジトリの制約
（stdlib 寄り・embed・CSP・zero-JS 切替 UI）と整合する**。全面適用の主な
コストは「機構」ではなく「文字列洗い出しとキー化の移行量」で、複数形や
カタログ管理が本当に欲しくなった段階で案A（x/text/message）への移行も
可能（テンプレート側は `{{t}}` 呼び出しのまま中身だけ差し替えられる）。
