# i18n（日本語/英語）適用の調査・設計メモ

調査・設計メモ。実装前の検討と、1画面プロトタイプの評価記録をまとめた。
`pull-requests.md` / `live-updates.md` 等と同じ形式。

問い:

> この MPA に i18n を適用したい。言語は**英語（デフォルト）と日本語**の 2
> つで十分。実施方法の選択肢を全部洗い出し、1 画面だけプロトタイプして
> 評価したい。

結論を先に書くと:

- おすすめは**案Cと方式②の組み合わせ**。案Cは薄い自作カタログ、
  方式②はcookie+`?lang=`によるスイッチャ。stdlibのみで済み、この
  コードベースの「依存を増やさない」「embedで単一バイナリ」の方針と
  一致する。将来フォーマットを育てたくなったら案A
  （`golang.org/x/text/message`）への載せ替えは小さく済む。
- プロトタイプは `/w/{ws}/issues`（一覧画面）に案Cを適用した。評価は
  末尾の「プロトタイプ評価」節。

## modern web guidanceで気にするべき事柄

`npx modern-web-guidance` で関連ガイドを検索・取得した結果、このアプリで
実際に効いてくるルールは以下（ガイドid付き）。

- **`html` / `accessibility`**: `<html lang>` は**ページの主言語に合わせて
  変える**（WCAG 3.1.1 Language of Page, Level A）。本文中で言語が変わる
  部分にはその要素に `lang` を付ける（3.1.2 Language of Parts, Level AA）。
  中身と違う言語コードを付けてはいけない — スクリーンリーダーが間違った
  言語で読み上げてしまう。現状 `layout.html` は `<html lang="en">` 固定。
  `hyphens` などlocale依存CSSの挙動も `lang` に連動する。
- **`ime-safe-enter-submit`**: 日本語入力では変換確定のEnterが
  keydownイベントとして届く。Enter-to-submitを自前で実装する場合は
  `event.isComposing` または `keyCode === 229` のガードが必須。本アプリの
  `enter-submit.js` はCtrl/Cmd+Enterでのみ送信するので素のEnterを拾わず、
  現状は非該当。「Enterで送信」する機能を将来足すときの注意事項として
  残す。
- **`translator` / `language-detection`**: ブラウザ内蔵の機械翻訳・言語検出
  APIは **volatile**（単一エンジン実装で仕様が変わりうる）で、ガイド自体も
  利用に明示的なopt-inを要する。zero-JavaScript方針とも衝突するため
  **採用しない**。案Eとして記録だけ残す。
- **日時・数の書式**: `fmtTime` が `"Jan 2, 2006 15:04"` で固定。ロケールごと
  の書式化が要る。ガイド `calculate-event-differentials` はブラウザ側
  `Intl.DurationFormat` の話だが、絶対時刻のみを表示する本アプリでは
  サーバ側で同じ問題を解くことになる。
- **キャッシュ**: `Accept-Language` でコンテンツを変えるなら
  **`Vary: Accept-Language`** を必ず出す。現行 `securityHeaders` のVaryは
  `Sec-Fetch-Site` / `Origin` のみ。

## 文字列の所在（現状調査）

「英語」が埋まっている場所はテンプレートだけではない。洗い出したもの:

| 層 | 場所 | 例 |
|---|---|---|
| テンプレート | `internal/web/templates/*.html` 全般 | "Issues" "New issue" "Open"/"Closed" "Previous"/"Next"、`aria-label`、`placeholder` |
| ビューモデル | 各ハンドラが組み立てる `Title` / `Heading` / `SubmitLabel` | `"New issue"`, `fmt.Sprintf("Edit issue #%d", id)` |
| バリデーション | `internal/store/validate.go` の `FieldErrors` | `"Title is required."`, `"Slug must match ..."` |
| エラーページ | `renderError*` の呼び出し箇所 | `"Form too large"` 等の heading/message |
| 日時 | `fmtTime`（web.go） | `"Jan 2, 2006 15:04"` |
| 静的 JS | `static/toast.js` / `partial-submit.js` 等 | `"Comment posted."`, `"Posting…"`, `"Comments (N)"` |
| フォールバック語 | `authorName` | `"anonymous"` |
| 列挙値の表示 | `store.HideReasons`、status バッジ | `"spam"` `"Open"` 等 |

一方**翻訳しないもの**: issueのタイトル・本文・コメントなどユーザー生成
コンテンツ（UGC）、workspace名、ラベル名。これらは投稿者の言語のまま出す。
コンテンツの言語を検出して `lang`/`dir` を付けるのが理想だが、今回の
2言語UIではスコープ外とする。

## 決めるべきことの分解

2つの直交する軸がある。

1. **言語をどう決めるか**（リクエスト → ロケール解決）
2. **メッセージをどこに置いてどう引くか**（カタログ + テンプレート結合）

### 軸1: ロケール解決方式

| 方式 | 仕組み | 長所 | 短所 |
|---|---|---|---|
| ① `Accept-Language` のみ | ヘッダを言語タグにマッチング | 実装最小 | ユーザーが上書きできない。「ブラウザ設定が ja だが英語で見たい」を解決できない（アクセシビリティ上も非推奨） |
| ② cookie + `?lang=` スイッチャ | `?lang=ja` で cookie を Set してリダイレクト、以降は cookie。未設定なら `Accept-Language` → `en` | 切替 UI が zero-JS で作れる（ただのリンク）。URL 構造を変えない | cookie 変更が GET に乗る（言語切替では一般的に許容）。`Vary: Accept-Language` は初回訪問のため要る |
| ③ URL パス prefix `/ja/...` | `/ja/w/x/issues` | 言語つき URL が共有できる。SEO に強い | mux の全ルートを prefix 配下に複製 or パターン書き換え。`issuesURL` 等の全 URL ビルダにロケールを通す。手数最大 |
| ④ アカウント設定 | `users.lang` カラム + 設定画面 | ログインすればどの端末でも同じ | 未ログイン（匿名可の本アプリでは大多数）に効かない。設定画面を作るコスト |

本アプリはlocalhost用途・匿名可・SEO不要。**② が現実解**。③ は「URLを
共有した相手と同じ言語で見たい」が要件に入ったときの再評価先。④ は
accounts Phase 2以降の任意拡張。

### 軸2: カタログ/実装案

| 案 | 内容 | 依存 | 複数形 |
|---|---|---|---|
| **A** `golang.org/x/text/message` | `message.NewPrinter(lang).Printf`、カタログは `message.SetString` でコード登録（または `gotext` で po 抽出）。CLDR 複数形あり | x/text（準標準） | あり |
| **B** `github.com/nicksnyder/go-i18n/v2` | TOML/JSON メッセージファイル + `Localizer`。go-i18n CLI でテンプレートから抽出 | 外部ライブラリ + ファイルフォーマット | あり（CLDR） |
| **C** 自作の薄いカタログ | ロケールごとの `messages` struct を Go ソースで持ち、フィールド名をそのままテンプレート関数名にする（`{{IssuesTitle}}`）。format 文字列は `fmt.Sprintf` で引数を取る | なし | なし（ja/en では手書きで十分） |
| **D** 言語別テンプレート複製 | `issues.en.html` / `issues.ja.html` を別ファイルでパース | なし | n/a |
| **E** クライアント側翻訳 | サーバは英語のまま、ブラウザの Translator API で表示時に翻訳 | なし（JS） | n/a |

各案の評価:

- **A（x/text/message）**: Goの「公式寄り」な答え。`language.Tag` の
  マッチング（`Accept-Language` パース）もx/textにある。ただしカタログ
  登録はコード生成/手書きGoが前提で、テンプレート文字列の抽出ツールは
  事実上 `gotext`（別ツール、go 1.x未対応期が長い）。プリンターはロケール
  ごとに要るのでテンプレート側は「ロケール別パース」か「`.T` をビュー
  モデルに載せる」かの設計が必要。
- **B（go-i18n）**: 機能は最も揃う（複数形・複合・ファイル監視）が、
  ja/enのみ・複数形ほぼ不要の本アプリには過剰。依存追加のコストに見合わ
  ない。
- **C（自作）**: カタログを `messages` struct（フィールド = メッセージ）
  でGoソースに持ち、`messageFuncs` がreflectで全フィールドを同名の
  テンプレート関数に登録する。`parsePages` をロケール別に回してその
  関数群をロケールに束縛するだけ。未翻訳フィールド（空文字）はenに
  フォールバックするので段階導入しやすい（一部画面だけ訳せる）。
  複数形は英語なら `one/other` の分岐程度で手書き可能（今回の画面に
  真の複数形はない）。
  - **JSONではなくGo structにした理由（レビュー指摘）**: JSONカタログ
    + `{{t "key"}}` ではキーのtypoが両面で検出不能（json側で綴りを
    間違えても、template側で間違えても静かにフォールバックするだけ）。
    struct + フィールド関数名ならカタログ側のtypoはコンパイルエラー、
    template側のtypoはパースエラーになる。
  - **代替: JSONカタログのままminigo lintでtypoを検出する**案もある。
    JS側でカタログを使う必要が出た場合はJSON保持が有利なので、
    `{{t "key"}}` とcatalogキーを突合するlintがあれば同等の安全性
    が取れる。
- **D（テンプレート複製）**: 機構が一番単純だが、**構造の複製**が2倍に
  なる。片方だけ修正し忘れる事故が確実に起きる。翻訳抜けの検出手段もない。
  除外。
- **E（クライアント翻訳）**: サーバ側コストゼロだが、modern-web-guidanceで
  volatile opt-in対象、単一エンジン、zero-JS方針違反、非対応ブラウザは
  英語のまま。除外。

### テンプレートへの束ね方（案C/A共通の設計点）

`funcMap` はパース時固定なので、リクエストごとのロケールを「見せる」方法
が設計の肝:

1. **ロケール別テンプレートセット** — `parsePages(locale)` でメッセージ
   関数群と `lang` をロケールに束縛して `pages[locale][page]`。
   テンプレートは `{{IssuesTitle}}` `<html lang="{{lang}}">` と書ける。
   **ビューモデルを一切変えずに `<html lang>` まで届く**のが利点。
   パースコストはロケール数倍（2言語なら実害なし）。
2. **ビューモデルに `T` メソッド** — `{{.T "key"}}`。データ側でロケールを
   運ぶので `layout.html` からも使えるが、全ページ構造体（15+）と
   `dict()` 経由のフラグメントに `T` を配線する必要がある。
3. **`{{t . "key"}}` で第1引数にデータを渡す** — パースは1組で済むが
   呼び出しが冗長になり、`dict()` で組み立てるフラグメントにも手動で
   `"T"` を詰める必要がある。

プロトタイプは **1（ロケール別セット）** を採る。ビューモデル無変更で
layoutまで訳せるため。

## 推奨案

- **言語解決**: ミドルウェア `withLocale`。優先順位
  `?lang={en,ja}`（cookieセット + `lang=` を除いたURLへ303）→
  `lang` cookie → `Accept-Language`（`ja*` ならja）→ `en`。
  ロケールはrequest contextに入れる。`Vary: Accept-Language` を追加。
- **カタログ**: 案C。`internal/web/i18n.go` に `messages` structと
  `messagesEN`/`messagesJA` を置く。`messagesFor(lang)` がカタログを、
  `messageFuncs` がテンプレート関数群を返す。
- **テンプレート**: `parsePages(locale)` でメッセージ関数群/`lang` を
  束縛したロケール別セット。`layout.html` の `<html lang>`、nav、
  footerと `issues.html` を訳す。言語スイッチャはヘッダnavに
  `?lang=ja`/`?lang=en` へのリンクを置く。他クエリの保持は後述の
  残課題で扱う。
- **ハンドラ側の文字列**: `Title`/`SubmitLabel` 等は `msgFor(r)` が
  contextに入れたロケールを使ってstructを取り、フィールドを直接
  参照する。
- **scope外（今回やらない）**: store層のバリデーションメッセージ、
  エラーページ文言、静的JSの文字列（toast等）、UGCの `lang` 付け。
  これらは全面適用時の課題として列挙する。

## 全面適用時の残課題（プロトタイプの外）

- store層 `validate.go` の `FieldErrors` をロケール非依存にするには、
  「エラーをコードで返してweb層でメッセージ化」か「ctxのロケールで
  storeが訳す」かの分岐が要る。前者がレイヤリングとして正しい。
- 静的JSの文字列は、CSP `script-src 'self'` がinline埋め込みを禁じて
  いるため、`<html lang>` をJSから読むか `data-*` 属性経由で渡すのが
  妥当。
- UGCの `lang`/`dir`: 理想は本文の言語を保存時に判定して `<article lang>`
  に出すこと。検出はgolang.org/x/textにない。whatlang系ライブラリか
  手掛かり実装が要る。
- `Vary: Accept-Language` を付けると、Speculation-Rulesのprefetchと
  キャッシュまわりの整合を再確認する。
- スイッチャリンク `?lang=ja` は現URLの他クエリ（`?q=` 等のフィルタ）を
  落とす。フィルタ保持が要件なら `Referer`/r.URLを使って組み立てる
  必要がある。

## プロトタイプ評価（案C、`/w/{ws}/issues`）

ブランチ `devin/*-i18n-prototype` に実装した。構成は上記「推奨案」どおり:

- `internal/web/i18n.go` — `messages` struct（フィールド = メッセージ
  1件）、`messagesEN`/`messagesJA`、`messageFuncs`（reflectで全
  フィールドを同名のテンプレート関数に登録）、`withLocale`
  ミドルウェア、`msgFor(r)`。
- `render.go` — `pagesByLang[locale][page]`（`parsePages(locale)` で
  メッセージ関数群/`{{lang}}` を束縛）、`executeLang` でフォールバック。
- `layout.html` / `issues.html` — `{{AppName}}`/`{{IssuesTitle}}` 等の
  フィールド関数呼び出しに置換。ヘッダに言語スイッチャ（`?lang=` リンク）。
- `issues.go` — `Title: msgFor(r).IssuesTitle`、`renderIssueList` に
  ロケールを渡す（他ページは既定en）。
- `securityHeaders` — `Vary: Accept-Language` 追加。

### 動作確認（実サーバ + curl + ブラウザ）

- `GET /w/default/issues?lang=ja` → 303 + `Set-Cookie: lang=ja`、別の
  クエリはリダイレクト先に保持される。
- `Cookie: lang=ja` → `<html lang="ja">`、見出し「イシュー」、タブ
  「オープン/クローズ/すべて」、件数「22 件中 1–20 件を表示」、フッタ
  訳文まで出る。
- `Accept-Language: ja`（cookieなし）→ ja描画。`Vary` に
  `Accept-Language` が載る。
- cookie `lang=fr`（未知）→ enにフォールバック。`go test ./internal/web`
  でi18n_test.go 7件 + 既存テスト全パス。
- 実ブラウザE2E（22件2ページ構成）でも切替・持続・復帰を確認済み。
- レビュー+E2Eで潰したバグ: ① `?lang=` リダイレクトが `//host/` パスを
  scheme-relative Locationとして通すopen redirect → `path.Clean` で
  解消。② ja `issues.count` が位置引数で語順を変え「1 件中 20–22 件を
  表示」と逆転 → `%[3]d/%[1]d/%[2]d` のインデックス指定で修正。
  5件1ページのseedでは検出不能だった。複数ページ構成での検証が
  有効だった。

### 良かった点

- **ビューモデル無変更**: メッセージ関数群/`{{lang}}` をパース時に
  束縛する形にしたので、15+ あるpage構造体にフィールドを足さず
  `layout.html` の `<html lang>` まで届いた。全面適用時もこの形で
  横展開できる。
- **段階導入が自然**: 未翻訳フィールド（空文字）はenにフォールバック
  するので、訳した画面だけjaになる「部分適用」が壊れない。
- **typoが構造的に起きない**: カタログはGo識別子、テンプレート参照は
  パース時に検査されるので、両面でtypoがエラーになる（JSON+`{{t}}`
  では検出不能だった）。
- **typed renderXxxが安全網になった**: シグネチャ変更に伴う修正漏れ
  （storybook）はコンパイルエラーで即検出できた。
- 2言語のテンプレートパース増は起動時の一回コストのみで体感なし。

### 痛かった点・見つかった制約

- **`{{if eq lang "en"}}` は関数値同士の比較になり常に不等** — `lang` は
  関数なので `{{if eq (lang) "en"}}` と括弧で呼び出す必要がある。一度
  はまりかけた。テンプレートの関数名は引数位置では自動呼び出しされ
  ない。
- **contextキーのiota衝突**: `contextKey` 型の `const x = iota` を別
  ファイルに置くとauth.goの `userContextKey` と同値0になりサイレントに
  キーが衝突する。キーごとに `struct{}` 型を切る形に修正（pitfalls.md
  にも記録）。
- **文中リンクはキー分割で妥協**: "Try a different keyword or <a>clear the
  filters</a>." は 3 分割にしたが、文末の "." がen語順を仮定していてja
  では "…フィルタをクリア." と半角ピリオドが残る。本格運用ではメッセージ
  内にリンクのプレースホルダを許す仕組みか、文全体をパーシャル化する
  設計が必要になる。
- **スイッチャは他クエリを落とす**: `/issues?q=x` 上で `?lang=ja` を踏むと
  `q` が消える。`lang` 以外をhrefに含めるにはリクエスト依存のURL生成が
  要るが、パース時束縛では渡せない。ビューモデルかヘッダでURLを組み立てる
  改修が必要になる。
- **`fmtTime` は英語フォーマットのまま**: "Nov 13, 2026 17:20 にオープン"
  と混在する。ロケール別書式はカタログではなくGo側の書式切替で対応する
  必要がある。
- **validation/エラーページ/JS文字列は未対応**: 422時のフォーム再描画で
  store由来の英語メッセージがja画面に混ざる。次にやるならここ。

### 評価まとめ

案C（messages structカタログ + ロケール別テンプレートセット +
cookie/?lang= スイッチャ）は**実装 ~250行のGo（カタログ含む）で
成立し、キーのtypoを両面で潰せる。このリポジトリの制約（stdlib
寄り・CSP・zero-JS切替UI）と整合する**。全面適用の主なコストは
「機構」ではなく「文字列洗い出しとフィールド化の移行量」で、複数形や
カタログ管理が本当に欲しくなった段階で案A（x/text/message）への移行も
可能。`messages` フィールド関数の中身をPrinter呼び出しに差し替える
だけでよい。
